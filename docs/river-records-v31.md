## Play Games configuration checklist

The source bridge builds against `play-services-games-v2:22.0.0` and the local Godot template AAR even while disabled. Its single `play_games_event(JSON)` signal carries request ID, account generation, current Play Games account ID, period, top/player score and rank, cached-state, submission outcome, or error. The Android calls run through the Activity UI thread; score buffers are copied then released. The GDScript service rejects stale account/period/retry results and keeps one cache per account+period.

The bridge is exported only after the owner supplies a real numeric Play Games game ID and six distinct nonempty leaderboard IDs. `platform/play_games_native/build_play_games.ps1 -GameId <real-id>` generates the app-ID string inside the selected AAR, writes an ignored hash receipt beside it, and the Editor export plugin requires that receipt’s game ID and SHA-256 to match the owner configuration. With defaults empty, no AAR, metadata, dependency, placeholder ID, or online prompt is added to an APK.

Configure the Android app link and OAuth credentials in Play Console, then create the ignored owner-only `addons/play_games/local_play_games_config.json` with `game_id`, the exact six-key `leaderboards` map, and optional `internal_testboard`. The debug build keeps public score submission disabled unless an explicit internal-testboard configuration is supplied. Only a fresh, finite, landed Android motion cast+hook+sensor-driven-fight catch may submit its rounded length in millimetres; migrated aggregates, capture fixtures, desktop/debug simulation, malformed data, duplicate catch tokens, and offline catches never backfill public boards. There is no persisted offline queue. Weekly and all-time query all six boards on each selection/retry; retained cache is marked cached while refreshing. Client validation is not cheat-proof.
